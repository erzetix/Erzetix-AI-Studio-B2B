# Технологический стек

## Язык реализации

Подсистемы комплекса реализуются на языке Python. Выбор обусловлен наличием официального Claude Agent SDK, на котором построена мультиагентная оркестрация, и составом библиотек для интеграции с внешними генеративными сервисами.

Интерфейс рабочего места команды реализуется средствами веб-стека.

## Оркестрация агентов

Мультиагентная оркестрация реализована на платформе **Claude Agent SDK** / **Managed Agents API** (Anthropic): координатор и набор специализированных агентов с индивидуальными настройками модели, системного промпта и набора инструментов для каждого.

**Claude Code** применяется на этапе разработки и сопровождения программного кода комплекса и не является компонентом промышленной эксплуатации.

## Распределение моделей по подсистемам

| Подсистема | Модель | Основание выбора |
|---|---|---|
| Ядро персонажа | Claude Sonnet 5 | Формирование контекста кампании с учётом параметров персонажа |
| Агент-аналитик трендов | Claude Haiku 4.5 | Обработка потоковых данных с последующей классификацией без задач генеративного характера |
| Агент-стратег | Claude Sonnet 5 | Планирование с учётом множества разнородных ограничений |
| Агент-креатор | Claude Sonnet 5 | Генерация текста с устойчивым воспроизведением стиля персонажа |
| Агент-визуализатор | Claude Sonnet 5 | Преобразование описательного текста в структурированные технические промпты |
| Агент-хранитель бренда | Claude Sonnet 5 | Основной цикл проверки материалов |
| Агент-хранитель бренда (эскалация) | Claude Opus 4.8 | Оценка неоднозначного контекста |
| Агент-аналитик метрик | Claude Haiku 4.5 | Обработка показателей эффективности публикаций |

## Принцип эскалации

Агент-хранитель бренда выполняет основной цикл проверки на модели Claude Sonnet 5. Эскалация на модель Claude Opus 4.8 предусмотрена для случаев, требующих оценки неоднозначного контекста: потенциальный репутационный риск, неочевидное нарушение требований бренда, конфликт между требованиями клиента и внутренними правилами допустимого контента.

Эскалация выполняется по решению подсистемы, а не для каждого материала. Такой порядок ограничивает издержки применения модели более высокого уровня возможностей при сохранении качества проверки в сложных случаях.

Условия эскалации определяются по результатам эксплуатации на Этапе 2 на основании фактической статистики случаев, в которых заключение основного цикла проверки потребовало пересмотра.

## Внешние генеративные сервисы

Для каждого типа задач предусмотрены основной и резервный провайдеры. Переключение выполняется API-оркестратором без изменения логики подсистем.

| Задача | Основной провайдер | Резервный провайдер |
|---|---|---|
| Изображение с максимальными требованиями к стабильности внешности | Higgsfield Soul 2.0 | Nano Banana Pro |
| Массовая генерация изображений, черновые варианты | Nano Banana 2 (Gemini 3.1 Flash Image) | Seedream 5.0 |
| Сложная композиция, рендеринг текста и элементов бренда | Nano Banana Pro (Gemini 3 Pro Image) | Seedream 5.0 |
| Видео | Kling 3.0 | Seedance 2.0 |
| Видео с требованием кинематографического качества и синхронизированного звука | Veo 3.1 | Kling 3.0 |
| Синтез речи | ElevenLabs | Яндекс SpeechKit |

Распределение провайдеров по задачам и назначение резервных провайдеров подлежат уточнению по результатам эксплуатации.

## Принципы работы с внешними сервисами

**Резервирование.** Отказ одного провайдера не приводит к остановке производственного конвейера. Задание направляется резервному провайдеру, указанному в составе объекта `GenerationTask`.

**Независимость от провайдера.** Логика подсистем не содержит обращений к конкретным сервисам. Подсистема формирует задание с указанием провайдеров, обращение выполняется API-оркестратором. Подключение нового провайдера не требует изменения логики подсистем.

**Фиксация в журнале.** Использование резервного провайдера фиксируется в журнале выполнения этапов с признаком `fallback_used`.

**Частичное выполнение.** Задания, не выполненные ни основным, ни резервным провайдером, возвращаются подсистеме-инициатору в составе перечня невыполненных заданий. Обработка остальных заданий продолжается.

## Контроль качества генерации

Соответствие сгенерированных материалов эталонным параметрам внешности персонажа оценивается агентом-визуализатором. Материалы, не достигшие порогового значения, направляются на повторную генерацию.

Метод оценки и пороговое значение определяются по результатам калибровки на реальных данных на Этапе 2.

## Валидация данных

Структуры данных, передаваемых между подсистемами, определены средствами библиотеки Pydantic. Валидация выполняется при передаче данных на вход каждой подсистемы. Несоответствие структуры прерывает обработку в точке возникновения.

## Инфраструктура

Облачное развёртывание с применением средств контейнеризации, обеспечивающих независимое масштабирование, развёртывание и обновление отдельных сервисов.

## Публикация контента

На текущем этапе размещение материалов в аккаунтах компаний на платформах и ввод показателей эффективности выполняются специалистами вручную, без прямой интеграции комплекса с API платформ.

Автономная публикация отнесена к последующим этапам развития продукта.
